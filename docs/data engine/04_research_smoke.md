# Phase 4 — Simple Research Smoke (детальное ТЗ)

> **Финальная фаза MVP** (см. `docs/00_master_plan.md`, секция «MVP Data Engine»).  
> Источник истины по объёму Phase 4 — этот файл и `docs/00_master_plan.md`.  
> `docs/strategy_constructor_master_plan.md` — только post-MVP направление для research-слоя; **в Phase 4 не реализуется** (ни registry стратегий, ни family/variant/instance, ни общий конструктор поверх `vectorbt`).

---

## 1. Цель фазы

**Прикладная цель:** чистые свечи из SQLite (после Phase 3: без дыр, валидный OHLC) **доходят до `vectorbt`**, на них строится минимальная стратегия, бэктест **завершается без исключений** и выдаёт **численные метрики** (не NaN), осмысленные на полном диапазоне данных.

**Техническая цель:** доказать end-to-end цепочку «БД свечей → чтение через существующий контракт → локальные индикаторы в research → `vbt.Data` → портфельные метрики», **без** расширения `data_engine/` индикаторами, адаптерами под `vectorbt`, кодом стратегий в core и **без** записи результатов бэктеста в SQLite.

**Не цель Phase 4:** архитектура индикаторов в движке, хранение индикаторов в БД, production-выбор indicator-библиотеки, realtime, FastAPI, Strategy Constructor, обобщённый `research/` framework.

---

## 2. Deliverable и команда

| Артефакт | Описание |
|----------|----------|
| **`research/ema_smoke.py`** | Единственный обязательный deliverable кода фазы: исполняемый скрипт (точка входа `if __name__ == "__main__"` или эквивалент), без установки пакета `research` как библиотеки в `data_engine`. |

**Команда запуска (acceptance и manual smoke):**

```text

```

Скрипт должен работать в окружении, где установлены зависимости группы research (см. §6). Путь к БД — через существующий `Settings` / тот же контракт, что и у CLI движка (не хардкод пути к файлу БД в репозитории).

---

## 3. Данные и контракт чтения

- Свечи читаются из SQLite тем же способом, что предусмотрен архитектурой после Phase 2–3: через **`Db.range_get(...)`** (или актуальный эквивалент store-уровня с тем же контрактом символа/ТФ/окна). **Phase 4 не вводит новых методов** в слой хранения; при необходимости только **использует** уже существующие API.
- Целевой smoke по умолчанию: **`BTCUSDT` / `1h`**, полный доступный диапазон в БД после `backfill` + `fix` (как в MVP acceptance мастер-плана).
- Предполагается контракт Phase 3: **`gaps_after = 0`**, OHLC валиден; после загрузки в `vbt.Data` **не допускается** появление NaN в колонках OHLC и в рядах, которые реально участвуют в расчёте сигналов/портфеля на прогоне (см. acceptance §10).

---

## 4. Стратегия и индикаторы

**Стратегия (единственная для этой фазы):** классический **EMA(20) / EMA(50) crossover** (например, длинная при пересечении вверх, выход или разворот при пересечении вниз — конкретная семантика входа/выхода фиксируется в скрипте и остаётся иллюстративной; важна воспроизводимость и отсутствие NaN в метриках, не «лучшая» торговля).

**Где считаются EMA:** **только локально** в `research/ema_smoke.py` (или в малом модуле-хелпере **внутри `research/`**, если скрипт разбит для тестируемости — см. §8), через **pandas**:

```python
pd.Series(...).ewm(span=20, adjust=False).mean()
pd.Series(...).ewm(span=50, adjust=False).mean()
```

(эквивалентно «одной строчке» на ряд с `adjust=False` — обязательное требование для сопоставимости с типичными реализациями EMA).

**Запрещено в Phase 4:**

- перенос расчёта EMA в `data_engine/`;
- запись EMA или любых производных индикаторов в SQLite;
- использование таблицы `indicators` (её может ещё не быть — создавать под Phase 4 **нельзя**);
- запись **любых** результатов бэктеста (сделки, equity curve, метрики) в SQLite — только stdout (и опционально stderr для отладки), без персистентного слоя.

## 5. Границы слоя `data_engine/` (жёстко)

В рамках Phase 4 **не добавляются** и **не появляются в репозитории** (если их ещё нет — не создаём; если есть заготовки — не расширяем под эту фазу):

| Запрещено | Комментарий |
|-----------|-------------|
| `data_engine/indicators/` | Indicator framework — Phase 5 **только если** отдельно решено вводить backend indicators (см. мастер-план, gate после Phase 4). |
| `data_engine/adapters/` в части `vectorbt` | Сборка `vbt.Data` живёт в `research/`, не в core. |
| Код стратегий, сигналов, бэктест-логики | Остаётся в `research/`, не в `data_engine/`. |
| Backend indicator storage, новые таблицы под метрики бэктеста | Не в Phase 4. |

Допустимые изменения в корне репозитория / `pyproject.toml` / тестах / `research/` — в рамках §6–§9. Явно **вне scope:** реализация полей из `docs/strategy_constructor_master_plan.md` (families, variants, оптимизатор, отчёты в виде продукта).

## 6. Зависимости (`pyproject.toml`)

- **`pandas`**, **`numpy`**, **`vectorbt`** подключаются **только** как **optional extras** для research (например, группа `research` / `dev` — имя группы фиксируется в реализации, но правило одно: они **не** являются обязательными зависимостями «голого» `data_engine` для Phase 1–3 сценариев).
- Правило мастер-плана сохраняется: **не поднимать** эти пакеты в core-зависимости движка и не импортировать `vectorbt` из `data_engine/`.

---

## 7. Manual smoke (обязателен)

Без успешного manual smoke фаза **не считается закрытой**.

Минимальный сценарий:

1. Чистая/известная БД или регламент: перед smoke выполнены `backfill` и `fix` для `BTCUSDT` / `1h` (как в Phase 2–3).
2. Установлены extras с `pandas` / `numpy` / `vectorbt`.
3. Выполнена команда **`python research/ema_smoke.py`**.
4. Зафиксирован результат (в коммите сообщения, в PR, или в внутренней заметке релиза): факт успешного завершения и **пример напечатанных метрик** (достаточно одной строки/набора чисел), без обязательной публикации полного лога.

---

## 8. Автотесты (`pytest`)

Тесты **обязаны** покрывать:

1. **Smoke-хелперы** — чистые функции, вынесенные из скрипта (например: сборка `DataFrame` свечей → колонки EMA → проверка отсутствия NaN после warmup-окна; либо мок `range_get` с синтетическими свечами → те же инварианты). Цель: регрессия «свечи + ewm → валидные ряды» без обязательного запуска полного `vectorbt` на каждом CI-ране, если это тяжело — тогда лёгкие тесты на pandas-часть + **отдельный** маркированный интеграционный тест опционально; минимум — хелперы и границы фазы.
2. **Границы фазы (structural / policy)** — автоматическая проверка того, что в diff-репозитории **не появились** запрещённые пути (например, отсутствие `data_engine/indicators/`, отсутствие `vectorbt` в импортах под `data_engine/`, отсутствие новых таблиц/миграций под индикаторы/бэктест — конкретная реализация: grep/pytest + список путей из §5).

Импорт `vectorbt` в тестах допустим **только** если он помечен как optional и CI устанавливает extra; иначе — тестировать без `vectorbt` там, где достаточно pandas-инвариантов.

---

## 9. Метрики на выходе скрипта

Минимальный набор для печати (числа, не NaN при валидных входных данных):

- **Sharpe** (или аналог из `vectorbt` с явной подписью, что именно считается);
- **Profit factor** (PF);
- **Max drawdown** (max_dd).

Дополнительные метрики — по желанию, не блокер фазы.

## 12. После Phase 4 — gate (смягчённый)

Закрытие Phase 4 **не означает** автоматический старт работ над indicator framework в `data_engine/` и **не обязывает** немедленно писать ADR-001/ADR-002.

**Обязательный выход:** есть живая цепочка «загрузили → починили → прогнали `vectorbt`», эмпирия по данным и боли локальных `pd.ewm` на нескольких индикаторах при необходимости.

**Отдельное решение (продукт/архитектура):** нужны ли **вообще** backend indicators в SQLite (единый слой в движке) или достаточно research-local расчётов ещё на долгий горизонт. Только при положительном ответе имеет смысл планировать **Phase 5** и закрывать ADR-001/ADR-002 **перед** реализацией indicator framework. При отрицательном — Phase 5 может быть отложена, сужена или заменена другими приоритетами (например, realtime только по свечам, расширение API и т.д.) — это уточняется в мастер-плане при пересмотре roadmap, не в этом ТЗ.

До принятия такого решения **индикаторный слой в core сознательно не трогаем**, чтобы не зафиксировать преждевременную архитектуру.
