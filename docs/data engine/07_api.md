# Phase 7 — Read-only API & Multi-Symbol (phase card / заглушка)

> Короткая phase card, не детальное ТЗ. Точный JSON-контракт, схемы snapshot-тестов, расписание scheduler-а, конкретные пороги stress-run-а — это уровень детального ТЗ Phase 7.

## Цель

HTTP-API на чтение, авто-проверка вчерашних суток ежедневно, несколько пар одновременно в realtime.

## Прикладной результат

Фронт/research/curl читают данные по документированному контракту через HTTP. Оператор не дёргает БД руками каждое утро. Одна машина обслуживает несколько пар одновременно.

## Зависимости

- Phase 6 (стабильный realtime на одной паре).

## Decision gates (обязательно до старта реализации)

- Жёстких ADR в Phase 7 нет.
- Точный JSON-контракт API фиксируется в детальном ТЗ Phase 7 и в `docs/api.md` **до** старта реализации.

## Возможное дробление

Phase 7 объединяет три темы (read-only API / scheduler / multi-symbol). Если на старте окажется, что объём кода даёт слишком крупный PR или фаза не читается за один присест, разрешено раздробить её на несколько шагов (например, API → scheduler → multi-symbol). Конкретная декомпозиция и acceptance каждого шага — в детальном ТЗ Phase 7. Сейчас фиксируется только право дробления.

## Что не делать раньше Phase 7

- Никакого FastAPI и роутов в Phase 1–6.
- Никакого apscheduler в Phase 1–6.
- Никакого multi-symbol manager-а до Phase 7. Phase 6 — один процесс, одна подписка.

## Что точно не трогать в Phase 7

- **Не вводить mutating endpoints.** API строго read-only — это DECIDED в мастер-плане; Phase 7 не имеет права это пересматривать.
- **Не делать ad-hoc SQL в роутах.** Все выборки идут через методы Db. Иначе следующий разработчик быстро превратит API в SQL-вьюшку.
- **Не объединять CLI и API в один путь записи.** CLI пишет через DIM; API только читает. Никаких пересечений.

## Ключевые открытые вопросы

- Точный JSON-контракт `/candles` и `/indicators`: поля, формат времени, пагинация.
- Авторизация: нужна ли минимальная API-key для прод или Phase 7 фиксирует «только localhost».
- Лимиты диапазона запроса.
- Что показывать в `/status` (кратко счётчики или подробная разбивка по парам/таймфреймам).
- Как именно разносить scheduler и realtime внутри одного процесса (детали — в детальном ТЗ Phase 7).

## Что появляется на уровне намерения (без файлов и тестов)

- read-only HTTP-API с документированным контрактом и snapshot-проверкой;
- ежедневный авто-fix вчерашних суток как фоновый job;
- realtime-manager, поддерживающий несколько подписок одновременно одним WS-клиентом.

Конкретные имена файлов/тестов, точные роуты, расписание job-а, конфигурация uvicorn, длительность dev-run-а — **уровень детального ТЗ Phase 7**, не уровень мастер-плана и не уровень этой phase card.
