# Phase 6 — Realtime (phase card / заглушка)

> Короткая phase card, не детальное ТЗ. Численные пороги (latency, watchdog-интервалы, размеры seed-буферов, тестовые tolerance) — это уровень детального ТЗ Phase 6, написанного **после** закрытия ADR-003 и **после** закрытия Phase 5.

## Цель

Движок работает в realtime: новые свечи и индикаторы обновляются сами; обрыв сети ничего не теряет.

## Прикладной результат

Процесс можно оставить запущенным, не заглядывать в БД и быть уверенным, что данные не разъезжаются.

## Зависимости

- Phase 5 (индикаторный слой как часть core, единый контракт, таблица `indicators`).

## Decision gates (обязательно до старта реализации)

- **ADR-003** — realtime indicator state (хранить state стрима в БД vs восстанавливать seed из истории при старте).

## Что не делать раньше Phase 6

- Никакого `realtime/`, никакого WS-клиента, никакого CLI `run` до Phase 6.
- Multi-symbol параллелизм — это Phase 7. В Phase 6 цель — один процесс, один WS-клиент, одна подписка.
- FastAPI / apscheduler / Parquet — Phase 7/8. В Phase 6 не появляются.

## Что точно не трогать в Phase 6

- **Не дублировать алгоритм поиска дыр.** Watchdog catch-up использует тот же путь, что и DIM (один алгоритм поиска дыр на весь проект).
- **Не делать второй путь записи свечей.** Realtime пишет в БД через тот же writer, что backfill и DIM. Никакого «отдельного INSERT-а специально для WS».
- **Не вводить ema-specific логику в `realtime/`.** Только generic-обработчик через индикаторный реестр.
- **Никаких прямых импортов indicator-библиотек в `realtime/`.** Изоляция в адаптерах продолжает работать.

## Ключевые открытые вопросы

- Как seed-ить indicator-стрим при старте manager-а. → ADR-003.
- Хранить ли сериализуемый state стрима между запусками. → ADR-003.
- Как catch-up-ить пропущенные свечи при долгом обрыве WS (общая идея — переиспользовать DIM на окно простоя; точные параметры окна и поведение пограничных случаев — детальное ТЗ Phase 6).

## Что появляется на уровне намерения (без файлов и тестов)

- WS-клиент с поддержкой реконнекта;
- realtime-обработчик закрытых свечей, пишущий через тот же writer, что и DIM;
- realtime-обработчик индикаторов, идущий через реестр, без знания о конкретной библиотеке;
- watchdog, который при простое подключения дёргает DIM-catch-up;
- CLI-команда запуска realtime.

Конкретные имена файлов/тестов, watchdog-интервалы, целевая latency «свеча в БД», политика seed (сколько баров, какая структура), точные тестовые tolerance для stream-vs-batch — **уровень детального ТЗ Phase 6**, не уровень мастер-плана и не уровень этой phase card.
