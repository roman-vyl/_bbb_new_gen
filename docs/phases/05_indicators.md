# Phase 5 — Indicator Framework (phase card / заглушка)

> Короткая phase card, не детальное ТЗ. До MVP детали индикаторного слоя на практике не подтверждены, поэтому здесь нарочно нет файлов, имён тестов и численных порогов. Конкретика — в детальном ТЗ Phase 5, написанном **после** закрытия ADR-001 и ADR-002 и **после** закрытия MVP.

## Цель

После MVP проект перестаёт считать индикаторы локально в research-скриптах. Появляется индикаторный слой как часть core: единый контракт, единая точка регистрации, явный статус готовности значения.

## Прикладной результат

Research, бэктест и (позже) realtime используют один и тот же источник индикаторов из БД, с понятной семантикой «это значение можно использовать в стратегии». «Руками посчитанная EMA внутри research-скрипта» уходит из проекта.

## Зависимости

- Закрытый MVP (`phase-4-done`): чистая БД свечей, работающий backfill+DIM, прошедший research smoke.

## Decision gates (обязательно до старта реализации)

- **ADR-001** — выбор библиотеки индикаторов.
- **ADR-002** — схема таблицы `indicators`.

В этих ADR закрываются: какая библиотека идёт в production-адаптер; как хранить multi-parameter и multi-output индикаторы; форма статус-модели; политика warmup; индексы; численные пороги для тестов корректности.

## Что не делать раньше Phase 5

- В Phase 1–4 не появляются: модуль `data_engine/indicators/`, таблица `indicators` в БД, зависимости под конкретные indicator-библиотеки в `pyproject.toml`.
- Никаких ema-specific хардкодов в DIM или в core engine. EMA в Phase 4 живёт внутри research-скрипта и в core не утекает.
- Никакого параллельного пути записи индикаторов мимо DIM/realtime. Записать индикатор «руками через Db» — нельзя.

## Ключевые открытые вопросы

- Какую библиотеку выбрать (`pandas-ta` / `ta-numba` / `streaming-indicators` / `TA-Lib` / собственный baseline). → ADR-001.
- Один backend на batch+stream или два разных адаптера. → ADR-001.
- Как хранить multi-parameter (`EMA(20)` vs `EMA(50)`) и multi-output (MACD, Bollinger) индикаторы. → ADR-002.
- Как формализовать warmup и статус готовности (поле `status`, политика по индикаторам, поведение при изменении периода). → ADR-002.
- Как DIM связывает свечи и индикаторы при ремонте окна (общая идея уже зафиксирована в принципах: DIM двухфазен, без рекурсии; конкретика — в детальном ТЗ Phase 5). → детальное ТЗ Phase 5.

## Что появляется на уровне намерения (без файлов и тестов)

- core знает об индикаторах только через интерфейсы и реестр; конкретный backend живёт изолированно в адаптерах;
- DIM расширяется ремонтом индикаторов в дополнение к ремонту свечей;
- research-скрипты переходят с локальных формул на чтение готовых индикаторов из БД.

Конкретные имена файлов/тестов, форма DDL, точные тестовые tolerance, численные пороги перфоманса, политика warmup-формул — **уровень детального ТЗ Phase 5**, не уровень мастер-плана и не уровень этой phase card.
