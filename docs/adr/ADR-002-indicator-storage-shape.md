# ADR-002 — Indicator Storage Shape

- **Status:** OPEN (stub)
- **Decision gate for:** Phase 5 — Indicator Framework
- **Author / owner:** TBD

> Этот ADR — **заглушка**. Будет наполнен и закрыт перед стартом Phase 5, до создания таблицы `indicators` в БД. Конкретный DDL, имена колонок и индексов в этом стабе сознательно не фиксируются.

---

## 1. Проблема

В Phase 5 в БД появляется таблица `indicators`. Её точная форма затрагивает:

- multi-parameter индикаторы (EMA(20) и EMA(50) под одним именем `ema`);
- multi-output индикаторы (MACD, Bollinger);
- индикаторы с разными источниками (`close`, `hlc3`, …);
- модель готовности значения (нужна явно, чтобы потребители не угадывали warmup);
- индексы для типичных запросов «дай мне индикатор для пары/таймфрейма на окне X».

Решить это **до** реализации важно потому, что хранение индикаторов — это самая массивная таблица в системе; миграции потом — это перегон гигабайт.

## 2. Зачем нужно решение

- Без формы таблицы Phase 5 не может стартовать: `IIndicatorBatch.compute(...)` некуда писать.
- Форма таблицы напрямую влияет на потребителей (vbt-адаптер, API), поэтому фиксировать её «как-нибудь» дороже, чем решить заранее.

## 3. Какие вопросы должен закрыть ADR

- **Форма ряда.** Long-form (`name`, `period`, `source`, …) vs wide-form vs long-form с дополнительной колонкой под multi-output.
- **Multi-parameter индикаторы.** Как кодируются параметры (только `period` + всё остальное в `name`, или `params`-поле, или отдельная таблица `indicator_specs`).
- **Статус-модель.** Какие статусы существуют, как они расставляются, что разрешено в `value` для каждого статуса.
- **Политика warmup.** Как вычисляется граница «WARMUP → READY» для разных индикаторов (включая multi-output) и где это правило живёт в коде.
- **Индексы.** Минимальный набор для типичных запросов и проверка на реалистичных объёмах.
- **Связь с realtime state.** Если ADR-003 решит хранить state стрима, надо учесть это здесь, чтобы не делать двойную миграцию.

Конкретные имена колонок, точный DDL, текст `CHECK`-ов, порядок колонок в индексах — это уровень финальной версии этого ADR, **не уровень стаба**.

## 4. Связь с другими решениями

- ADR-001 — выбор backend влияет на доступные warmup-данные и форму multi-output.
- ADR-003 — realtime indicator state может потребовать дополнительные структуры в БД.
- `docs/00_master_plan.md` — DECIDED: candles и indicators хранятся отдельно. OPEN: точная схема `indicators`.
- `docs/phases/05_indicators.md` — phase card.
