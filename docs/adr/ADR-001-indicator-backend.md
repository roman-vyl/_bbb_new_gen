## 1. Проблема

В v2 нужен индикаторный слой, покрывающий минимум EMA, RSI, ATR, MACD, Bollinger и расширяемый под новые индикаторы без переписывания core. Свой stateful-класс на одну EMA — нормально; на RSI/ATR/MACD «руками» — это путь к собственной полу-библиотеке теханализа и второму легаси.

Архитектурное решение «core знает только об интерфейсах + adapters/» уже принято (см. `docs/00_master_plan.md`, секция DECIDED). Этот ADR закрывает один открытый вопрос: **какую конкретно библиотеку использовать в production-адаптере**.

## 2. Зачем нужно решение

- Без выбора backend нельзя приступить к Phase 5: индикаторный слой не может быть «совсем абстрактным», у него должна быть реальная реализация.
- Решение влияет на зависимости в `pyproject.toml`, на установку под Windows + Python 3.x, на покрытие нужного набора индикаторов и на возможность streaming-режима в Phase 6.
- Чем дольше тянуть — тем больше шанс, что выберется случайно (из соображений «давайте уже что-нибудь поставим»).

## 3. Кандидаты на оценку (стартовый список)

> Список можно расширить в процессе spike-а. Версии и состояние пакетов проверять на момент запуска spike-а.

- `pandas` — baseline, всегда присутствует как reference.
- `pandas-ta` — широкое покрытие; bulk-ориентирован.
- `TA-Lib` — классика; native C-обёртка, болезненная установка под Windows.
- `ta-numba` — Numba JIT; заявляет bulk + streaming.
- `streaming-indicators` — узко под realtime, stateful API.

## 4. Какие вопросы должен закрыть spike и финальная версия ADR

- Установка и эксплуатация на нужных платформах (Windows + актуальные версии Python) без хаков.
- Покрытие минимально-необходимого набора индикаторов проекта.
- Поддерживает ли backend batch и/или streaming (или нужны два разных адаптера).
- Стабильность API и возможность сериализовать состояние стрима (требование для ADR-003).
- Корректность относительно baseline-реализации.
- Производительность на реалистичных размерах данных.
- Лицензия и активность репозитория.

Конкретные численные пороги (скорость, корректность, размер тестовой выборки) — фиксируются в методике spike-а и в финальной версии этого ADR, **не в этом стабе**.

## 5. Возможные исходы

- Один backend закрывает и batch, и streaming → один адаптер.
- Разные backend-ы для batch и streaming → два адаптера, интерфейсы изначально разделены.
- Все кандидаты не проходят чек-лист → fallback: baseline для batch + минимальный собственный stateful-набор для streaming. Это явное проектное решение, фиксируется здесь.
