# ADR-003 — Realtime Indicator State

- **Status:** OPEN (stub)
- **Decision gate for:** Phase 6 — Realtime
- **Author / owner:** TBD
- **Date opened:** TBD
- **Date decided:** —

> Этот ADR — **заглушка**. Будет наполнен и закрыт перед стартом Phase 6. Размеры seed-буферов, целевая cold-start latency, формат сериализации в этом стабе сознательно не фиксируются.

---

## 1. Проблема

В Phase 6 на каждую закрытую свечу для каждого зарегистрированного индикатора вызывается `update(value)` стрима — это stateful вызов: у каждого стрима внутри живёт текущее состояние (например, для EMA — последнее значение и счётчик баров warmup-а).

Открытый вопрос: **что делать с этим состоянием между запусками процесса.**

## 2. Зачем нужно решение

- Без него не понятно, как вообще стартует manager realtime: с пустыми стримами и долгим разогревом или мгновенно.
- Решение влияет на форму таблицы индикаторов (см. ADR-002) и на требования к backend-у индикаторов (см. ADR-001) — поэтому должно быть закрыто до старта реализации Phase 6, а не «по ходу».

## 3. Варианты на рассмотрение

- **(A)** Восстанавливать seed из истории при старте manager-а. State в БД не хранится. Простая модель, чистый рестарт; cold-start медленнее.
- **(B)** Хранить сериализуемый state в БД после каждого `update()`. Cold-start быстрый; state-схема жёстко связана с конкретным backend-ом и требует миграции при смене.
- **(C)** Гибрид: хранить state, но при несовпадении версии/сериализации — fallback на seed-из-истории.

## 4. Какие вопросы должен закрыть ADR

- Какой из вариантов выбираем и почему.
- Если хранится state — где (отдельная таблица или колонка в `indicators`), как именно сериализуется, как обрабатывается версионирование при смене backend-а.
- Контракт seed-операции (что именно подаётся на вход стриму при cold-start).
- Поведение manager-а на cold-start: общий порядок шагов и что считается «готов работать».

Конкретные размеры seed-буферов, целевые cold-start latency, имена таблиц/колонок — это уровень финальной версии этого ADR.

## 5. Связь с другими решениями

- ADR-001 — выбор backend (если решаем хранить state — это требование уходит обратно в ADR-001).
- ADR-002 — схема `indicators` (если для state нужна отдельная сущность, она проектируется и закрывается в ADR-002, чтобы не делать двойную миграцию).
- DECIDED в мастер-плане: realtime пишет в БД через тот же writer, что и DIM; индикаторный backend изолирован в адаптерах.

## 6. Когда закрывается

Перед стартом Phase 6 (после `phase-5-done`).
